# Mail / Calendar completion: decisions awaiting the owner

This document covers **5A only**. Calendar 5B is not started or authorized by this PR. No private accounts, addresses, message samples or investment data belong here.

| Decision | Options | Recommendation / safe default |
| --- | --- | --- |
| Scheduled delivery feasibility | Gmail UI-native scheduling; API-controlled private Gmail draft plus digest; encrypted immutable MIME in a private single-owner expiring store | Gmail's public API has no native schedule-send method. A mutable draft reference does not freeze approved content. Deliver only the disabled UI, metadata schema and SQL transition model now. No enqueue RPC, dispatcher, sender identity, encrypted payload or body store. |
| Future immutable payload privacy | Refuse changed provider drafts; immutable MIME encrypted per owner outside shared CRM; avoid persistence altogether | No shared-body persistence. No encrypted MIME/attachment payload persistence without a separately approved retention, key-access, quota, deletion and legal-hold contract. A hash is not a recoverable payload. |
| Immediate exact-copy send | Send an existing mutable draft; send the exact reviewed MIME; write/update then send then delete | Use one messages.send of reviewed MIME. Gmail has no draft revision compare-and-swap; sending the mutable draft could race another client. Retain source draft and explain it in confirmation. Deletion requires a separate review. Existing flag-off drafts.send remains unchanged. |
| Chunked attachment transport | Durable private object store; provider resumable session; transient process-local chunks | Keep the existing 2 MiB / 10-file budget. Transient caller-bound RAM only, 256 KiB chunks, ten-minute expiry, no provider URLs. Loss/restart/cross-instance routing fails closed. Durable/large uploads require another privacy/deployment decision. No retry loop. |
| Review ledger retention | Short TTL purge; retain protected outcomes; owner-reviewed archival policy | Metadata only. Expire pending approval to cancelled; unfinished claimed operations become uncertain, never queued again. Preserve completed/uncertain records; schema rollback refuses all reviews. Duration and audited repair/archival require owner approval. |
| Revocation across services | Assume SQL and Google are atomic; explicit pre-dispatch fence and in-flight ambiguity | SQL atomically checks active member, feature, permission, connection epoch, actual granted scopes, approval expiry and cancellation. Immediately execute one Google request. After the dispatch fence, cancellation/revocation cannot recall an accepted request: report uncertain and require human review. Never claim a SQL row lock spans the HTTP request. |
| Gmail wake-up signal | Browser polling/manual refresh; authenticated Pub/Sub invalidation | Keep push route 503 and no watch registration. Future OIDC audience/issuer/service-identity checks, bounded owner/cursor dedupe, IAM/topic ownership, watch renewal/expiry, quotas and invalidation-only browser delivery need review. Never cache bodies in the signal queue. |
| Optional rollout | Enable globally; per-member owner provisioning | Global flag false and canonical mail_completion permission absent. Owner can canary only approved internal Workspace test accounts. Each real mutation needs the user's separate explicit confirmation. |

The existing relationship-only GitHub Actions worker remains read-only and unchanged. A future scheduled sender must be a **different purpose-bound job**, not an extension of that worker or a generic HTTP/MIME sender. The future job must accept one reviewed queue UUID, validate its immutable revision/alias/attachments/due time, obtain a single-use claim, revalidate immediately before dispatch, send once, and settle or quarantine uncertainty. No such job exists here. The current design table cannot be written through the Data API and the scheduling button stays disabled even when mail completion is enabled.
