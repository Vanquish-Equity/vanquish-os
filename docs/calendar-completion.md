# Phase 5B — reviewed Calendar completion

Prerequisite: main c92a818, including 20261016013701_mail_completion. This phase is independent of the Gmail implementation and adds no sender, worker capability or OAuth scope. The optional calendar_completion permission is owner-provisioned by SQL; existing Admin permission RPCs are unchanged. private.calendar_completion_configuration.enabled defaults false. Without BOTH gates the Calendar DOM, readers, editor and occurrence-only behavior remain the baseline. Missing migration/state read failure also retains that mode. Revoking either gate blocks every new review/dispatch server-side.

## Scopes and provider access

Exact prefix: https://www.googleapis.com/auth/. The owner reports one production connection with calendar.events and calendar.readonly (plus existing Gmail scopes). These suffice for all new provider capabilities; production credentials/grants were not inspected during implementation. No new scopes are requested. If calendar.events is missing, the reviewed writer returns **Reconnect Google in Settings** while existing reading and new availability remain possible with readonly.

| Capability | Exact scopes used | Additional checks |
| --- | --- | --- |
| CalendarList membership / actual accessRole | calendar.readonly | Each ID is resolved through caller users/me/calendarList.get, not arbitrary email lookup |
| Event/master read | calendar.readonly; calendar.events additionally required before preparing writes | Caller-owned token, current calendar membership; bounded JSON |
| Create/edit/delete, series, drag/resize, RSVP | calendar.events; calendar.readonly for CalendarList authorization | Writer/owner accessRole, real Google ACL, current ETag and explicit final confirmation |
| Free/busy | calendar.readonly | 1–12 distinct calendars present in caller CalendarList, no group expansion, maximum 31 days |
| CRM tasks overlay | No Google scope or Tasks API | Active caller, feature permission/current connection, INVOKER SQL and existing task/parent RLS |

The provider also supports other broader/narrower scopes; this implementation deliberately checks the two already granted Calendar scopes, without requesting more. Primary references: [CalendarList.get](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/get), [events.patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch), [event resources / attendeesOmitted](https://developers.google.com/workspace/calendar/api/v3/reference/events), [ETags](https://developers.google.com/workspace/calendar/api/guides/version-resources), [freeBusy.query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query).

## Review → confirmation → one execution

Every new save/delete/RSVP, including a proposed drag or resize, first creates a private metadata review. UI shows original/final dates, timezone, explicit scope, ETag, title/content, RRULE, guests, notification policy and potential recipients (including removed guests/organizer when applicable). Google service notifications may still follow its own policies even with sendUpdates=none; the UI does not promise suppression of all mail. The final Checkbox/Confirm is separate from preparing the review.

The server rebuilds the mutation from the request and fresh caller-owned Google reads during execution. SHA-256 binds normalized dates/zone, content, RRULE, guests/response, notifications, target/scope, source ETag, Meet/reminder and exact provider PATCH/POST body. A changed fingerprint is refused before any write. The provider request uses the reviewed If-Match. New events have stable compatible IDs and Meet request IDs. No create-then-edit chain is hidden behind confirmation.

private.calendar_mutation_reviews stores only UUID, canonical owner key, operation, resource hash, revision hash, connection epoch hash, state and timestamps. No event descriptions, titles, attendees, calendar addresses, times, Google tokens or payloads are persisted. The request carries the reviewed content; no flow depends on process RAM or instance affinity. Closing/losing a request loses the UI payload, not the durable fence. Own metadata history supports cancellation and uncertainty review.

The new optional GoogleError.status field preserves the provider HTTP status without changing transport code mappings/messages or adding retries. A definite 4xx (including 412/429; excluding ambiguous 408) closes that review as cancelled via the rejected transition. The UI may correct input/access/quota, prepare a NEW review and explicitly confirm again. A 412 conflict is displayed and requires reopening; no force overwrite. A timeout/network failure/408/5xx, malformed success or failure to record an attempted outcome is uncertain. No automatic retry, reclaim or fallback occurs. An uncertain resource hash blocks new reviews until an owner-approved reconciliation policy exists. If outcome recording itself fails, the durable claim remains fenced; expiry never requeues it. A late cancellation that has already made an outcome uncertain cannot be relabelled rejected merely to unlock it.

States: pending → claimed → completed; pre-fence cancel → cancelled; post-fence cancel/lost result → uncertain; clear rejection from claimed/started → cancelled. The same review cannot execute twice, including after a definitive rejection. A new confirmation is necessary. Completed decisions permit legitimate later edits with new provider state. Pending/claimed/uncertain resource reviews are unique per owner/resource hash. Approval lasts ten minutes; listing expires at most 100 rows and returns at most 25. Creation is limited to 60 reviews/hour/owner. Metadata retention remains open; no automatic protected-record deletion.

Each authorization RPC uses FOR SHARE on the active member, explicit permission, singleton flag and current connection. The final dispatch fence repeats those checks, scopes, revision, cancellation and expiry immediately before ONE provider mutation. Locks end with the RPC, before HTTP. A revocation/cancel after dispatch cannot transactionally recall Google; report uncertainty. No SQL/HTTP atomicity or exactly-once claim. Own metadata cancellation/outcome/history remain available to active owners after permission/connection revocation, so pause does not hide unresolved decisions. No event data can be accessed through those cleanup operations.

## Recurrence, gestures and RSVP

Expanded events require an explicit **This occurrence / Whole series** choice, initially empty. Whole series loads the master ID, dates, guests, recurrence and master ETag; it never patches the instance ID with a master's ETag. A displayed-instance gesture is applied as a time delta to the selected master only after that explicit choice. Existing exceptions may be affected by Google's series semantics; connected tests are outstanding. Unsupported/locked/cancelled/special event types or omitted/over-budget guest lists fail visibly. Use Google directly for unsupported recurrence.

RRULE is a strict subset: DAILY/WEEKLY/MONTHLY, interval 1–12, exactly one COUNT (1–366) or UNTIL (real date, at most 366 days from start). Weekly BYDAY is an allowlisted unique weekday set; monthly BYMONTHDAY is 1–31; WKST is allowlisted. Duplicate/unknown fields, endless rules, multiple rules, EXDATE/RDATE passthrough and invalid dates are refused. COUNT bounds occurrence count, not a one-year horizon for sparse monthly rules. Occurrences cannot change recurrence. Timed recurrence preserves the explicit IANA zone; all-day dates remain distinct/exclusive-ended.

Day/week timed cards offer pointer move/resize proposals in 15-minute increments. Alt+Up/Down moves; Ctrl+Alt+Up/Down resizes on the main card; the resize handle also supports Alt arrows. A touch-sized date-selector button offers move/extend/shorten SelectMenu choices. The editor provides exact date/time inputs as another alternative. No gesture commits to Google, and cancelling its review leaves Google unchanged. Reduced-motion styles apply to new controls. Month/agenda/all-day edits use the same reviewed date selectors rather than ambiguous grid gestures.

RSVP resolves the fresh event and permits only exactly one attendee marked self by Google, excluding organizer-self. PATCH contains only that self response and attendeesOmitted=true, leaving other responses intact. Occurrence/series choice and notification confirmation still apply. Read-only shared calendars do not become writable merely because a button exists.

## Bounded reads and task view

Each new provider JSON response is capped at 512 KiB and uses the existing 20-second request timeout. No new provider pagination loops. Reviews cap request content at 26,000 JSON characters, guests at 100 and event duration at 31 days. Availability checks each selected CalendarList entry, disables group expansion and accepts at most 500 busy intervals/calendar. Only clipped busy start/end pairs and an unavailable status are returned, never event titles, guests or descriptions. Missing/provider-error calendars are unavailable, never assumed free. The UI explicitly labels its maximum 31-day UTC slice; this may be shorter than the displayed 42-day month grid.

Task overlay is a caller-RLS read of public.tasks, not a new event source or synchronized copy. It shows open/unarchived tasks assigned to the current canonical member email, bounded to 50 days and first 200 rows (201st only detects partial). Legacy unassigned/owner-text tasks are not silently reassigned. Explicit Deal/Company access and invoker parent visibility supplement task RLS. Titles are capped at 500 characters. Task cards appear on their dates and in the dated view panel. No task mutation, Google Tasks scope or event creation occurs. Correlated record checks remain correlated for correct per-parent authorization; policy calls are wrapped in scalar SELECT, while identity-only policy calls use initplans. A new partial assignee/due index supports this read.

## SQL, pause and protected rollback

Migration 20261016211212 follows the applied 5A migration. It preserves all seven existing permission literals and adds calendar_completion; private.calendar_completion_baseline captures the exact CHECK for rollback. All three new private tables have RLS, no direct authenticated grants, and restrictive machine_identity_isolation using scalar SELECT in USING and WITH CHECK. Every function rejects machines. Public RPCs are SECURITY INVOKER; private definers touch authorization/review metadata only, never events or privileged task reads. Auth machine identities/read worker are unchanged.

The combined phase-5b-calendar-completion.sql is one begin/commit transaction and matches the migration via scripts/check_phase_sql.py. Any forward failure reverts it. All DROP/DELETE statements are marked. Rollback commits the pause before attempting removal; ANY protected review blocks removal, leaving it paused and preserved. Empty-only removal drops 5B objects/index/grants and restores the exact pre-5B CHECK, retaining mail_completion and earlier permissions. It never repairs/deletes protected decisions or changes earlier phases. Operational recovery is normally pause/retain, not destructive rollback.
