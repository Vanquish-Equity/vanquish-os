# Phase 5A: Gmail completion

Prerequisite: main 311afa8 / Phases 0–4, including Auth service-worker isolation. This PR changes Gmail only. No Calendar feature, read-worker capability, OAuth scope request or push endpoint is changed. The owner flag and mail_completion permission default off/absent. Without both, the existing mailbox/composer remains in its original mode, including immediate drafts.send, its existing limits and confirmation. No Google mutation was executed during implementation, verification or CI.

## Exact scopes and provider contracts

All calls are caller-owned users/me, with fresh server-only credentials and no shared tokens. The configured OAuth base already requests gmail.readonly, gmail.modify and gmail.send. Actual refreshed grants are checked per action; production grants have not been inspected. Missing grants yield a reconnect-in-Settings message. No gmail.settings.basic, mail.google.com, Calendar or new scope is added to OAuth configuration.

| Capability | Accepted exact scope suffixes under https://www.googleapis.com/auth/ | Do configured base grants suffice? |
| --- | --- | --- |
| Verified send-as list (read only) | gmail.readonly or gmail.modify; provider also accepts gmail.settings.basic | Yes; no new settings scope requested |
| Full forward body and attachment reference verification | gmail.readonly or gmail.modify | Yes |
| Create/update/discard private Gmail draft | gmail.modify or gmail.compose; alias read also needed | Yes, through gmail.modify |
| Send reviewed exact MIME with messages.send | gmail.send or gmail.modify or gmail.compose; draft read and alias list also needed (readonly/modify, or compose for draft read) | Yes |
| Legacy drafts.send | Provider requires gmail.modify or gmail.compose, not gmail.send alone; unchanged legacy path currently also has modify in the configured base | Yes through modify; no claim that send alone suffices |
| Chunk staging | No provider scope; active caller, feature permission and current connection epoch required for every chunk | No extra scope |
| Scheduled-send design / push-disabled UI | No provider request exists | No new scope requested |

Primary references: [sendAs.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs/list), [sendAs verification](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs), [messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send), [drafts.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/send), [drafts.create](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/create), [uploads](https://developers.google.com/workspace/gmail/api/guides/uploads), [push](https://developers.google.com/workspace/gmail/api/guides/push).

Alias GET uses a response field mask and 64 KiB limit, max 50 entries, and includes **only verificationStatus=accepted** addresses. Unknown/pending status is denied, including an unexpected primary response; connected-provider verification of this field is outstanding. No send-as creation, SMTP settings or arbitrary From text is exposed. The server rereads choices during review and execution. Changing From requires another draft save/review. Rich HTML uses a strict parser allowlist: text, formatting, links and tables, no images (including tracking pixels), scripts, event attributes, styles, forms or iframe. Exact sanitized content is shown in a sandboxed CSP-restricted review iframe.

## Interactive mutations: explicit review, one provider write

The gated composer separates **Review save**, **Review send** and **Review deletion**. A dirty/new draft must be saved, then reopened before sending; no chained save-then-send mutates Google twice behind one click. The member sees final To/CC/BCC, verified sender, subject, sanitized body, attachment names/bytes, operation and immediate timing. A Checkbox and final Confirm action are required. Edits invalidate/cancel the current review. Reviews expire after ten minutes. A reference/digest-only private ledger binds owner, operation, canonical content/attachment hash, provider draft ID and connection epoch. Neither SQL nor logs receive message text, subject, recipients, alias values, MIME, attachment bytes or resumable URLs. Owner identity is the canonical membership key; the ledger is not a shared CRM timeline.

Before execution, the server rereads the draft/forward attachment parts from the same caller's Gmail, validates selected references and sizes, revalidates the alias and reconstructs the fingerprint. It claims once, refreshes the caller's Google client/scopes, and calls the SQL dispatch fence immediately before **one** provider request. A source revision mismatch is refused. For send, the operation is messages.send with the reviewed MIME, not a late mutable drafts.send reference; concurrent edits after the read cannot substitute different recipients/content. The source draft is retained. No automatic draft cleanup/delete occurs. The send-once partial unique index prevents a second review of a completed/claimed/uncertain source draft. Pending reviews can be cancelled explicitly in metadata-only history; never fork an uncertain operation into another attempt automatically.

Database membership/config/permission/connection rows are locked FOR SHARE during each authorization RPC, and the review row FOR UPDATE serializes claim/cancel/fence. **These locks end when that RPC commits, before HTTP.** Revocation/cancellation before the fence blocks the request; after the fence the request is in flight and cannot be recalled reliably. A late cancel produces uncertain, never cancelled/no-delivery. No cross-provider atomicity or exactly-once delivery is claimed. A transport error, timeout, malformed success, or failed outcome recording after attempting the write is uncertain and never retried. Even an apparently definitive provider rejection is quarantined conservatively after dispatch begins. The UI blocks further writes and asks for owner review of Gmail/Sent. If membership deactivation prevents recording the result, the claim stays fenced and metadata history converts an expired claim to uncertain when the member can next access it; an owner may mark it uncertain while paused. It is never reclaimed. A confirmed save requires reopening, rather than treating a failed follow-up read as permission to create another draft.

Immediate review states: pending → claimed → completed, with dispatch_started_at as the irreversible fence; pending/claimed-before-fence → cancelled; claimed-after-fence → uncertain on lost result/late cancellation. Completed, uncertain and cancelled cannot be claimed. Completion/uncertainty recording and own pre-dispatch cancellation remain available to active owners after a feature/permission/connection revocation so that an outcome is not hidden by a pause; these metadata operations never contact Google. Nonmembers, inactive members, machines and other owners are denied. Own history returns at most 25 rows and never bodies; each call expires at most 100 decisions through an owner/expiry partial index.

Existing label/archive/trash behavior remains the prior implementation, outside the new composer/forwarding mutation path; this PR does not silently broaden or rewrite those capabilities. Legacy actions retain their existing no-auto-retry behavior. New reviewed calls are independently protected server-side, not just by a disabled button.

## Forwarding and transient chunks

Forward with attachments rereads the selected caller-owned message. It returns sanitized HTML and message/part references; saving validates every reference again and fetches bytes only from verified parts in users/me. No caller-supplied attachment URL is followed. Removing a retained attachment removes its reference before review. Attachment IDs use the existing wide attachment-ID validator, not the shorter message-ID validator. Inline CID rendering is removed by the strict sanitizer; files remain attachments. Oversized/unsupported messages fail visibly and should be handled in Gmail, not truncated and silently sent.

Limits: 100 MIME parts, 200,000 body characters, ten files, **2 MiB aggregate** across new/retained/forwarded files, 200-character filenames in staging and source metadata, 256 KiB sequential chunks, ten-minute absolute upload expiry. Each owner reserves at most 2 MiB across at most four process-local sessions; global reservations cap at 16 MiB. Chunks require exact offsets, known file length/index and the current owner/connection epoch. No overlap, out-of-order write, automatic retransmit or cross-owner release is allowed. Session UUIDs are opaque local identifiers, never Google resumable URLs or credentials. Delete/expiry zeroes stored chunk buffers on a best-effort basis. Copied temporary processing buffers are garbage-collected; this is not a forensic memory-erasure guarantee.

Staging is **ephemeral RAM**, not encrypted-payload persistence, filesystem, Supabase Storage or shared CRM cache. Timers delete expired sessions in a live process; every access also enforces expiry. Serverless eviction/restart or a different instance loses the session: fail closed and ask the user to reselect files. This is bounded chunk transport, not a durable/provider-resumable upload guarantee. Selected bytes are used only after explicit member selection/review. Direct enhanced draft lookup caps at four pages of 500; legacy lookup default is unchanged. New JSON response reads cap at 4 MiB, attachment JSON at 3 MiB, alias/mutation responses at 64 KiB; provider requests use the existing 20-second transport timeout. Attachment fetches are sequential, max ten per preparation. Approval's ten-minute deadline is checked again before dispatch. No arbitrary unbounded provider pagination is added.

## Scheduling and push: deliberately not live

Scheduling button is disabled even with completion enabled. private.mail_scheduled_design is an inaccessible metadata-only prototype: queue UUID, owner, private Gmail draft reference, confirmed revision, confirmation/due timestamps and state. It contains no payload or payload reference. There is no enqueue RPC, sender entry point, watch call or new machine capability. The SQL-only transition validator models pending → claimed/cancelled; claimed → sent on confirmed dispatch; claimed → cancelled before dispatch or uncertain on late cancellation/lost result. Sent/cancelled/uncertain are terminal. The existing relationship-only Auth worker is rejected by every new helper and RPC. [Open decisions](mail-calendar-open-decisions.md) specify the future one-purpose job without implementing it.

/api/integrations/gmail/push is unchanged: 503 before parsing or DB access. A future push channel would validate Pub/Sub OIDC/audience/issuer/service identity, dedupe bounded owner/history references, and invalidate/reload through authorized reads. It must never contain/cache bodies. Topic ownership/IAM, watch creation and renewal before provider expiry, quotas, denial/expiry tests, a separate purpose-bound identity and explicit activation approval are required. No GCP resource or subscription is created here.

## SQL, security and rollback

Migration 20261016013701 follows Phase 4. Canonical member_permissions CHECK is extended only for mail_completion, with exact baseline captured for rollback. All new tables are private, RLS-enabled, have zero direct authenticated grants and restrictive machine_identity_isolation with scalar SELECT in USING and WITH CHECK. All new functions deny machine identities. Public readers/mutators are INVOKER wrappers over narrow private metadata-only helpers with empty search paths and revoked PUBLIC/anon execution. No public definer, credential-returning RPC, private message store or worker capability is added. There is no new worker role/migration prerequisite because no worker is introduced.

The rollback first commits enabled=false, then refuses schema removal if any review/design metadata exists. Thus a failed rollback leaves the feature paused and protected decisions intact. With empty tables only, it drops Phase 5A objects, removes only Phase 5A permission grants and restores the previous permission constraint. No existing Gmail/Calendar/Auth/CRM function or data is rewritten. Every DROP/DELETE is marked. There is no automatic repair or deletion of uncertain outcomes. The default operational recovery is pause and retain schema.
